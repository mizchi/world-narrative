# Jev による世界設定判定の初期実験

実行: 2026-10-03 01:43 JST。返された実モデル名: `jev-1.13.0`。ルーブリック: `lore-v1`。初回計測の原本は [集計](../results/initial/summary.json) と [生レスポンス](../results/initial/raw.json)。入力の [全件バッチ](../results/initial/all-payload.json)、[参照ラベルを含むケース](../results/initial/fixtures.json)、[ソースのハッシュ](../results/initial/manifest.json) も保存した。

## 検証したこと

四ジャンルで各8件、計32件のオリジナルの候補を作り、以下を別々に判定した。

- `consistency`: 正史と両立する／明確な矛盾／成立の保証に必要な情報が足りない。
- `hook`: 具体的なプレイヤーの行動と観察または結果が記述されているか。
- `leak`: 指定された開示条件より前に作者の秘密をプレイヤーへ明言しているか。

各世界の8件は、正史の矛盾、誤信・虚偽資料、遊びへつながる状況、未定義の条件に依存する保証、背景だけの追加、早期開示、未確定の仮説、許された作用の境界のケース。

参照ラベルは本実験の作者が設定した。独立した人間によるアノテーションや、校正用／評価用の分割は行っていない。「情報不足」の分類には、未定義の条件を採用前に確認するという編集方針も含む。**一般の作品での正答率を測った実験ではない。**

実装は [fixtures.ts](../src/fixtures.ts)、[judge.ts](../src/judge.ts)、[jev.ts](../src/jev.ts)、[benchmark.ts](../src/benchmark.ts)。ラベルと判定理由は state に含めない。`noul >= 0.5` を分類表示に使い、自動採用の閾値としては使用しない。

## 結果

| 投げ方 | 呼出回数 | 整合性の参照ラベルと一致 | 行動の記述 | 早期開示 |
| --- | ---: | ---: | ---: | ---: |
| 全32件、初回 | 1 | 31/32 | 32/32 | 32/32 |
| 全32件、同条件で再実行 | 1 | 32/32 | 32/32 | 31/32 |
| 全32件、候補と選択肢の順序を反転 | 1 | 31/32 | 32/32 | 32/32 |
| 世界ごとに8件をバッチ | 4 | 31/32 | 32/32 | 32/32 |
| 候補ごとに1件ずつ | 32 | 30/32 | 32/32 | 32/32 |

初回は明示的な矛盾4件を全て拾い、矛盾の誤検出は0件。誤った信念・資料の4件も弾かなかった。これらは少数の明瞭なケースに限った結果である。

初回の誤りは `archive.4`。距離も行為の所要時間もないのに「10秒で移動して犯行を終えられる」という保証を、成立する候補に分類した。確率は compatible 0.37 / contradiction 0.30 / underdetermined 0.33、confidence 0.05 で、分布はほぼ割れていた。再実行では情報不足へ変わった。

別の問題は `station.4`。回復条件を未定義とした怪異について、翌朝06:00の回復を保証する候補が、世界ごとのバッチと個別判定では compatible になった。confidence はそれぞれ0.53 / 0.51。未確定の条件を新しい定義として受け入れる読みと、採用前に確認すべき保証として読む方針の境界がある。

提示順を反転した条件では `archive.8` を矛盾と判定した。死後に自動送信された予約メールは、死亡後に本人が行動したことを必要としない。初回は compatible 0.79、反転後は contradiction 0.55。候補と選択肢の順序を同時に変えたため、どちらの効果かは分離できない。

同条件の再実行でも96判定中2件が反転した。初回 `archive.1.leak` は0.49、再実行は0.51で表示上の分類が変わった。この候補は作者用の時系列であり、本来はプレイヤーへ開示されない。境界に近い値をそのまま自動処理へ使う設計は避ける。

`hook` の一致は、明示的な行動と結果を認識したことを示すだけで、遊びが実行可能・魅力的だと証明するものではない。矛盾する設定にも行動の記述は存在し得るよう、二つの問いを分離した。

## 時間と入力量

| 投げ方 | 通信と検証の時間 | 入力トークン |
| --- | ---: | ---: |
| 全32件、初回 | 417 ms | 31,399 |
| 全32件、再実行 | 305 ms | 31,399 |
| 世界ごと、4回の合計 | 792 ms | 32,218 |
| 候補ごと、32回の合計 | 6,030 ms | 52,175 |

ログ保存等も含む逐次実行の壁時計時間は、世界ごとのバッチが797 ms、候補ごとの個別判定が6,069 msで、今回の計測では約7.6倍の差になった。個別呼出し側も3問を一つにまとめているため、比較しているのは96回対4回ではなく、32回対4回である。

ベンチマーク39リクエスト全体の入力は178,590トークン、出力は13,846トークン。料金は今回取得・確定していないため表示しない。

実験の順序は固定されており、ネットワーク、接続の温まり方、サーバー負荷を分離していない。世界ごとのバッチは4標本、全件バッチは2標本のため、安定した p95 やサービスの性能保証として扱わない。全件バッチでは別候補も state に含まれることによる文脈の混入を排除できない。

## 設計に反映すること

1. 初期実験の範囲では、局所的な意味の一次検査をバッチ化する価値がある。
2. 時間・量・回復条件などの未定義項目は、モデルの confidence に頼らず、コントラクトと未確定事項への参照から保留できるようにする。
3. 機械的に成立を確認できる自動処理や予約を、死亡後の人物の行為と区別して記録する。
4. 作者用の記述とプレイヤー向けの提示を、文体だけでなくデータの構造で分ける。
5. 自動採用を実装する前に、長い因果、時間・分岐、複数提案の統合、文脈取得漏れ、自然な文章の秘密漏洩、長さと順序の個別対照を含む評価用コーパスを作る。

同じケースへ何度も合わせ込むと検証にならないため、この実験では失敗後に質問やラベルを修正して数字を上げることはしていない。

別途、並列ライターによる二つの長い提案を7問・1リクエストで確認した。その結果と限界は [統合レビュー](../examples/ash-estuary/review.md) に記録した。32ケースの参照ラベル一致率には含めていない。

## 再実行

```sh
pnpm install
just check
just benchmark-dry
# API キーが設定された環境で
just benchmark
```

`~/.profile` からキーを使用して実行した。キーをソース、リクエスト保存、結果ファイルへ書いていない。実 API は TypeSafe に送信される。現在のスクリプトは実験向けで、自動リトライやサイズ超過の分割は持たず、失敗時はエラーとして停止する。

再実行すると `results/raw.json` と `results/summary.json` を更新する。初回計測の固定記録は [初期実験の保存ディレクトリ](../results/initial/) に置く。
