# 並列ライターの制作手順

最初に、[アーキタイプ](archetypes.md)から構築の起点を選び、プレイヤーが何をするゲームかを決める。神話から始める場合も、最初の凍結時点には調査・移動・交渉・介入などの動詞と、選択の結果が必要。

## 基礎を凍結する

統合担当は初期World、ゲームの変数・時間・地理・開示規則、作者未確定の範囲を作る。人物からなら欲望と関係、事件からなら出来事と証拠、ハードSFなら資源と制約を先に固定する。どの起点でも、作者の真実と人物が信じることを分ける。

担当には同じ版のWorld、ブリーフ、生成したJSON Schema、担当のnamespaceを配布する。実例は [灰潮のブリーフ](../examples/ash-estuary/brief.md) と [world.json](../examples/ash-estuary/world.json)。

```sh
pnpm narrative schema --out .tmp/schemas
pnpm narrative init .tmp/production --world examples/ash-estuary/world.json
```

## 担当を分ける

地域・事件・人物の関係など、局所の変更をまとめて一人のライターへ渡す。時間や資源を使うEpisodeは、操作と結果まで同じ担当が作る。別の担当がその品質を読む場合は、書き込む提案を増やさずレビューを返す。

| 担当 | 例 | 返すもの |
| --- | --- | --- |
| 地域ライター | 南の水門、北の採石場 | 局所要素とEpisodeを含むProposal |
| 人物ライター | 欲望、誤信、相反する義務 | Entity / Claim / AssertionのProposal |
| 謎・証拠ライター | 資料、目撃、反証 | 資料と情報取得操作のProposal |
| レビュー担当 | 初見の理解、選択の意味、既視感 | 問題箇所と改善案。正史へ直接書かない |

全担当が同じ正史ファイルを編集する運用は避け、統合担当が逐次採用する。共通の述語・規則・変数の追加が必要なら、局所案へ混ぜず統合担当に契約変更を要求する。

## ライターへ渡す指示

以下をブリーフと組み合わせる。

> 指定の正史版を基準に、担当namespace内の要素だけを追加するProposal JSONを返してください。既存要素のID、時間、資源、開示条件を守り、本文で依存する事実もreadSetに含めてください。追加Assertionはproposedとし、真実・誤信・資料を分けてください。未確定事項を勝手に解決しないでください。
>
> Episodeには、プレイヤーが確かめられる具体物、実行条件と費用のある行動、選択で変わる結果を入れてください。良い結果にも失うものや後に残る課題を示してください。作者用の説明を本文へ移さず、秘密を含む断片にはdisclosedClaimIdsと適切な条件を付けてください。writeSetにはActionとFragmentも含め、notesに解釈・保留・制作上の調整を残してください。

機械で検査できる範囲と、読み手の体験を分けて考える。選択肢の数が多いだけで魅力的になるとは限らない。プレイヤーが判断材料を見つけ、自分の理由で選び、その結果を理解できるかを試す。

## 統合する

各提案をpreviewし、必要ならJevで文章と宣言の食い違いを確認する。Jevがclearでも、作者が採用理由を残す。サンプルの二提案は [tide.proposal.json](../examples/ash-estuary/tide.proposal.json)、[quarry.proposal.json](../examples/ash-estuary/quarry.proposal.json)。

一案の採用後、他案は明示的にrebaseする。参照の変更があれば担当へ返す。変更がなくても全体の到達性を調べ、訪問順・時間・共通資源の干渉を確認する。Jevの判定は新しい世界に対して取り直す。

最後にゲームを出力し、初見の読み手が遊ぶ。理解しにくい情報、意味の薄い選択、意図しない正解への誘導をレビューする。機械の整合性検査は、この読者テストを置き換えない。
